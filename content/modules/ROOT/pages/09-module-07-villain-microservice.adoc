= Module 7: The Villain Microservice
:source-highlighter: rouge
:toc: macro
:toclevels: 1

Every super hero needs a nemesis. OpenCodeQuest Corp must now create the service that manages super villains. This time, the code is developed with Quarkus' **Spring compatibility layer** -- to show that Quarkus can accommodate Spring code without major modifications.

There is an extra twist: a super villain has sneaked into the code and introduced a **malicious dependency**! You will need to detect and fix the problem using Advanced Cluster Security.

== Learning objectives

By the end of this module, you will be able to:

* Bootstrap a Quarkus service with Spring Web and Spring Data extensions
* Understand the difference between native Quarkus and Spring annotations in Quarkus
* Identify a CVE intentionally introduced in the CI/CD pipeline
* Fix a vulnerable dependency and redeploy

== Spring compatibility in Quarkus

Quarkus provides Spring compatibility extensions that map Spring annotations to optimized native Quarkus APIs:

* `quarkus-spring-web` -- Spring MVC (`@RestController`, `@GetMapping`, etc.) → RESTEasy
* `quarkus-spring-data` -- Spring Data JPA (`JpaRepository`) → Hibernate Panache
* `quarkus-spring-di` -- Spring DI (`@Autowired`) → ArC (CDI)

IMPORTANT: The Spring compatibility extensions **do not load the Spring application context**. They map Spring annotations to CDI/RESTEasy equivalents. Third-party Spring libraries will not work.

== Exercise 2: Explore the Villain service structure

Unlike the Hero service, Spring annotations are used here.

. Open `src/main/java/io/quarkus/workshop/villain/VillainController.java`. Note the Spring annotations:
+
[source,java]
----
@RestController                          // Spring @RestController (mapped to JAX-RS)
@RequestMapping("/api/villains")         // Spring @RequestMapping (replaces @Path)
public class VillainController {

    private final VillainRepository repository;

    public VillainController(VillainRepository repository) {
        this.repository = repository;
    }

    @GetMapping                          // Spring @GetMapping (replaces @GET)
    public List<Villain> getAll() {
        return repository.findAll();
    }

    @GetMapping("/random")
    public Villain getRandom() {
        return repository.findRandom();
    }

    @PostMapping
    @Transactional                       // Standard Jakarta EE
    public Response create(@Valid Villain villain, @Context UriInfo uriInfo) {
        repository.save(villain);
        // ...
    }

    @PutMapping
    @Transactional
    public Villain update(@Valid Villain villain) {
        return repository.save(villain);
    }

    @DeleteMapping("/{id}")
    @Transactional
    public void delete(@PathParam("id") Long id) {
        repository.deleteById(id);
    }
}
----

. Open `VillainRepository.java`. It extends `JpaRepository` (Spring Data):
+
[source,java]
----
public interface VillainRepository extends JpaRepository<Villain, Long> {

    @Query("SELECT v FROM Villain v ORDER BY RAND()")
    @Transactional
    Villain findRandom();
}
----
+
NOTE: `JpaRepository` is provided by the `quarkus-spring-data` extension. Quarkus automatically generates an implementation for all standard CRUD methods.

== Exercise 4: Houston, we have a problem!

At this point, you will observe a **pipeline failure**. The `acs-image-check` step fails.

image::acs-check.png[align="center",link=self,window=blank,width=600,title="The acs-image-check step fails -- a security policy is violated"]

A super villain has sneaked into the code and introduced an unauthorized dependency in `pom.xml`!

. Click the failed step to view the logs:
+
image::acs-image-check-error.png[align="center",link=self,window=blank,width=600,title="Violation details -- a CVE dependency was detected by ACS"]

. The error message indicates which dependency violates the policies.

. In Dev Spaces, open the `pom.xml` file. Thanks to the **Red Hat Dependency Analytics** extension installed in Dev Spaces, the problematic dependency is automatically underlined:
+
image::devspaces-CVE.png[align="center",link=self,window=blank,width=600,title="Red Hat Dependency Analytics automatically underlines the vulnerable dependency in pom.xml"]

. Remove the problematic dependency from `pom.xml` (it is not used in the code).

=== Verify

After removing the dependency, verify the project still compiles:

[source,bash]
----
./mvnw compile -q && echo "Compilation OK"
----
